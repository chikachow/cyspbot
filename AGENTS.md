# Repository agent guidance

## Workflow

1. **Ground the task.** Inspect the worktree, affected source and tests, and the references triggered below in proportion to the task. Establish the requested outcome, governing contracts, and overlapping modifications before editing; preserve unrelated tracked and untracked work.
2. **Complete the requested work.** Resolve routine choices from repository evidence and carry prior agreement forward while its assumptions remain valid. Ask when unresolved requirements materially affect public contracts, compatibility, recovery, scope, or authorization; continue work that does not depend on the answer. For implementation, establish the intended behavior from the request and governing contracts, then align code, tests, and owned documentation with it. For reviews and plans, deliver analysis without unrequested implementation.
3. **Verify and review.** Follow [validation scope](CONTRIBUTING.md#validation-scope), then review the whole diff against the requested outcomes and affected failure paths. For implementation, resolve actionable in-scope findings and rerun affected checks. For reviews, support findings with triggers, consequences, and evidence; distinguish defects, unmet outcomes, unresolved contract questions, and optional improvements.
4. **Hand off with evidence.** Report each requested outcome, checks performed, and verification limits. Distinguish finished implementation from completed verification and readiness under the applicable contribution or release gates. If genuinely blocked, identify remaining work, the blocker, reasonable safe alternatives attempted, and the input or access needed. Commit, push, publish, or deploy only within the user's authorization.

## Design and contracts

- Choose the simplest cohesive design for the affected concern, including callers and lifecycle transitions. Preserve required behavior, public contracts, and lifecycle guarantees; distinguish these from existing implementation choices. Weigh concrete benefits against migration, regression, review, and maintenance costs.
- Preserve established domain, API, and protocol terminology. For terminology or trust-boundary changes, read [CONTEXT.md](CONTEXT.md); rename internal symbols only for a concrete correctness or comprehension benefit.
- Extract helpers when they expose a coherent operation or lifecycle boundary, remove meaningful duplication, or clarify callers. A test seam needs behavioral evidence that justifies its interface and maintenance costs. For package boundaries, Worker entrypoints, bindings, or runtime changes, read [Implementation](docs/implementation.md).
- Before adding defenses or removing safeguards, identify the reachable failure scenario and required guarantees, compare simpler alternatives, and explain consequential tradeoffs and maintenance costs. A credible, consequential failure can justify an in-scope safeguard without a prior incident or known probability; uncertainty alone neither justifies nor disqualifies it. Where later trust or lifecycle decisions depend on validated values remaining stable, preserve them for that interval using the simplest adequate mechanism, such as ownership, encapsulation, copying, or immutability.
- For HTTP behavior, webhook acceptance, job classification, queue acknowledgement or retry changes, read the affected [service contract](docs/service-contract.md) sections. For authentication, external input, token exchange, permissions, or logging changes, read [SECURITY.md](SECURITY.md); for issuer or broker binding changes, also read [runtime bindings](docs/implementation.md#runtime-bindings). Validate consumed external values at their owning trust boundary, including newly crossed boundaries; TypeScript types alone do not establish trust. Apply closed-field validation only where the contract requires it.
- For routing, Wrangler configuration, deployment automation, or artifacts, read [Deployment](docs/deployment.md). Keep source-owned defaults separate from production configuration; the root Wrangler configuration is a test harness. Local fixtures and dry runs do not by themselves verify live service configuration or end-to-end production behavior.
- Use the pinned runtime, package manager, scripts, and generators. Keep dependency, formatting, and generated changes necessary to the concern. Regenerate affected environment declarations from Wrangler configuration rather than hand-editing them.

## Evidence and documentation

- Ground implementation claims in source or direct experiments and external compatibility claims in primary sources or direct experiments. State what was and was not verified.
- Choose independent behavioral evidence at the affected boundary, including rejection, retry, and acknowledgement paths. When consolidating tests, account for retained guarantees and justify consequential coverage removed. To claim a regression test detects a defect, observe it fail against faulty behavior with unchanged expectations and pass after the fix.
- For documentation changes, follow [documentation ownership](CONTRIBUTING.md#documentation-ownership). Keep each fact and policy authoritative in one place, with explicit task-triggered pointers. Keep evaluation history and completed plans with their change records. Repository guidance must remain usable without personal agent configuration.
